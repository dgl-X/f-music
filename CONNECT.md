# Family Music Connect

Экспериментальная функция позволяет выбрать, где играет музыка, и управлять
этим плеером из другого WEB- или Android-клиента того же аккаунта.

## Как включить

Сервер 0.1.32 / Android 1.0.56 показывает в WEB отправку команды, потерю связи с API и
состояние удалённого воспроизведения. Отправка команды не означает её выполнение:
плеер подтверждает результат отдельным ACK. Android-отчёты дополнены безопасным
блоком `connect` с состоянием связи, эпохой, задержкой команды и возрастом
последнего контакта; события смены владельца и повторов ACK находятся в журнале.

Начиная с версии 0.1.32 состояние различает намерение Play (`playing`)
и фактическое воспроизведение (`is_playing`). При `buffering=true` или ожидании
аудиофокуса счётчик удалённого плеера не движется; кнопка паузы остаётся доступной.
Если старый клиент не передаёт новые поля, действует прежняя семантика `playing`.

Начиная с версии 0.1.32 доступен персональный переключатель
«Настройки → Аккаунт → Family Music Connect». Он хранится в PostgreSQL и
действует для WEB/Android одного аккаунта. Выключение оставляет текущее аудио
играть локально на выбранном устройстве, отменяет ожидающие команды и освобождает
Connect-владельца; незавершённую передачу сначала требуется закончить.
Повторное включение не запускает аудио и не восстанавливает старые команды.
Новые клиенты повторно проверяют доступность примерно каждые 15 секунд.
Старым клиентам после повторного включения может потребоваться перезапуск.

Общий серверный флаг остаётся верхней границей доступности:

В `.env` сервера задайте:

```dotenv
MUSIC_CONNECT_ENABLED=true
```

Перезапустите `family-music`. Старые клиенты продолжат работать: новые маршруты
добавлены в API v1, а функция по умолчанию выключена.

## Как это работает

В сервере 0.1.31 и Android 1.0.54 реализована двухэтапная передача для клиентов
с capability `transfer_prepare`. Функция остаётся экспериментальной и выключена
по умолчанию; включается оператором для контролируемой полевой проверки.

1. Клиент регистрирует случайный ID, имя, тип и возможности устройства.
2. Polling раз в 1,5 секунды одновременно служит heartbeat и каналом команд.
3. «Слушать на…» отправляет целевому плееру очередь, текущий трек и позицию.
4. Новый клиент подготавливает аудио на паузе, ждёт готовность и завершение
   перемотки, затем отправляет ACK с фактическим состоянием. Сервер назначает
   подготовленный плеер и направляет прежнему команду остановки. Только после
   подтверждения остановки прежнего устройства выдаётся `activate` новому;
   позиция продолжения берётся из остановленного источника, если трек совпадает.
   Старые клиенты без capability сохраняют прежний одноступенчатый контракт.
5. Play/pause, переходы, seek, shuffle, repeat и громкость направляются активному
   устройству. Аудио не проходит через управляющий клиент.

Команды ограничены аккаунтом и живут 30 секунд. При потерянном ACK команда может
быть доставлена повторно, но клиент сохраняет результат её первого выполнения и
повторяет только ACK. Состояния применяются по монотонной серверной ревизии, а
исходящие снимки одного клиента отправляются последовательно. Каждая передача
увеличивает `playback_epoch`: сервер и клиенты отклоняют снимки и команды от
предыдущего владельца плеера. WEB требует явного нажатия кнопки Connect перед
приёмом воспроизведения из-за browser autoplay policy.

При подготовке локальный плеер не публикует промежуточную очередь и позицию в
Connect или сохранённое состояние. WEB не заменяет собственные shuffle/repeat
настройки при отображении удалённого плеера. Передача с управляющего устройства
на любое третье устройство использует снимок активного удалённого плеера.
Отложенный снимок привязан к эпохе, в которой был создан: его нельзя отправить
с новой эпохой и перезаписать состояние нового владельца.
Обычные удалённые команды во время передачи получают `connect_transfer_pending`,
чтобы play/next не запустили приёмник до подтверждённой остановки источника.

ACK перемотки содержит подтверждённую позицию; обычные команды с фактическим
снимком обновляют серверное состояние только для текущего владельца и эпохи.
Истёкший ACK или неподтверждённая подготовка отклоняются. Отсутствие ACK остановки
источника оставляет новый плеер на паузе: автоматический запуск при сетевой
неопределённости не выполняется. Восстановление такого незавершённого переноса
и отдельная UI-индикация передачи требуют дополнительной полевой проверки.

Быстрый список «Слушать на…» показывает только устройства, которые сейчас
online и объявили готовность принимать воспроизведение. Закрытые вкладки WEB
остаются в истории устройств до отзыва или серверной очистки, но не засоряют
переключатель.

Активное устройство владеет плеером, пока присылает heartbeat. Если heartbeat
не приходит 35 секунд, сервер атомарно освобождает владельца, помечает состояние
остановленным и отменяет его ожидающие команды. Вернувшийся плеер либо другое
устройство может занять новую `playback_epoch`; старый снимок уже не перезапишет
нового владельца. Управляющий WEB-клиент возвращает свою локальную карточку, но
не запускает звук автоматически, чтобы краткий сетевой обрыв не создал два
одновременно играющих плеера.

Серверный smoke-тест выполняется отдельным обычным аккаунтом без доступа к
музыке: `CONNECT_TEST_USERNAME=... CONNECT_TEST_PASSWORD=... npm run
test:connect:smoke`. Тест проверяет повторную доставку до ACK, идемпотентный ACK,
смену эпохи, отклонение старого снимка и отмену команды прежнего владельца, после
чего удаляет созданные им виртуальные устройства. В CI тот же сценарий запускает
собственный API и одноразовый PostgreSQL командой `npm run
test:connect:integration`.

## Ограничения первого MVP

- транспорт пока HTTP polling, без WebSocket;
- Android принимает команды через `PlaybackService`, независимо от открытого
  экрана Activity; ОС всё ещё может остановить процесс без активного
  воспроизведения, поэтому готовность устройства определяется heartbeat;
- функция выключена по умолчанию; оператор может включить её для контролируемой
  полевой проверки гонок передачи, быстрых переключений и потери сети;
- WEB и Android игнорируют повторный snapshot с той же ревизией, чтобы polling
  не сбрасывал локальный плавный отсчёт позиции;
- Android восстанавливает переданную очередь в порядке списка ID, независимо от
  порядка ответа `/tracks/resolve`, и выбирает текущий элемент строго по ID;
- `shuffle_order` передаёт точную перестановку ID, а `playback_history` — историю
  переходов; сервер сохраняет их в необязательном `navigation_json`, фильтруя
  отсутствующие ID. Android устанавливает Media3 ShuffleOrder, WEB восстанавливает
  свой navigator; следующее и предыдущее воспроизведение не перемешиваются заново;
- освобождение владельца после длительного offline реализовано; восстановление
  после реальных Wi-Fi/LTE-разрывов проходит полевую проверку.
