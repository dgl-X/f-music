# Архитектура Family Music

Документ предназначен одновременно для владельца проекта и для разработчика, который продолжит работу без истории чата.

## Цель

Самостоятельный закрытый музыкальный сервис для небольшой семьи. OpenVK не используется и не является зависимостью проекта.

## Принципы

1. Оригинальный аудиофайл никогда не изменяется.
2. Физический файл отделён от пользовательской библиотеки.
3. API является единственным источником серверных данных для WEB и Android-приложения.
4. Сервер можно запустить на одном хосте без Kubernetes.
5. Любая долгая операция позднее должна перейти в фоновую очередь.
6. Каталог общий для всех зарегистрированных пользователей; лайки, плейлисты и история персональны.

## Компоненты MVP

- `src/server.js` — HTTP API, статика, загрузка и Range streaming.
- `src/db.js` — PostgreSQL и автоматическое создание схемы.
- `src/security.js` — пароли, токены, cookies и Content-Range.
- `public/` — web-клиент без стадии сборки.
- `storage/uploads` — временные части.
- `storage/originals` — принятые аудиофайлы.
- `storage/covers` — извлечённые JPEG-обложки.

Простой web без React выбран намеренно: на первом этапе нет frontend toolchain и большого дерева зависимостей. После стабилизации API UI можно заменить независимо.

## Авторизация

`POST /api/setup` доступен только пока таблица `users` пуста. Он создаёт единственного первого администратора. Обычной регистрации нет.

После настройки администратор управляет семейными аккаунтами через `GET/POST /api/users`. Новые аккаунты создаются обычными пользователями без административных прав; самостоятельно зарегистрироваться нельзя.

`PUT /api/me/password` меняет собственный пароль после проверки текущего и завершает остальные сеансы пользователя. `PUT /api/users/{id}/password` позволяет администратору назначить новый пароль другому пользователю и завершает все его активные сеансы.

`POST /api/login` создаёт случайный 256-битный токен. Клиент получает его как `HttpOnly; SameSite=Strict` cookie. В таблице `sessions` хранится только SHA-256 токена.

Неудачные входы ограничиваются по IP (8 попыток за 15 минут). Изменяющие запросы с cookie принимаются только с совпадающим `Origin`; внешний протокол и имя хоста передаются доверенным reverse proxy.

## Протокол загрузки MVP

1. `POST /api/uploads` с `{filename,size,mime_type}`.
2. Сервер создаёт запись и пустой `.part`, возвращает `id` и `offset`.
3. `HEAD /api/uploads/{id}` возвращает `Upload-Offset`.
4. `PUT /api/uploads/{id}` принимает одну часть с заголовком `Content-Range: bytes start-end/total`.
5. `start` обязан совпасть с подтверждённым сервером `received_bytes`.
6. Последняя часть атомарно переводит загрузку в `processing` и создаёт запись в `processing_jobs`.
7. Фоновый worker выполняет SHA-256, `ffprobe`, извлечение обложки и финализацию; клиент опрашивает `GET /api/uploads/{id}`.

Если SHA-256 уже присутствует, временный файл удаляется, а ответ содержит `duplicate: true` и ID существующего трека. Оригинал физически хранится только один раз.

Протокол близок по назначению к TUS, но не заявляет совместимость с ним. Перед Android-клиентом следует либо оформить текущий протокол как стабильный `/v1`, либо перейти на `tusd`.

Задания очереди сохраняются в PostgreSQL. После рестарта задания со статусом `processing` возвращаются в очередь. Ошибка повторяется до пяти раз с экспоненциальной задержкой, после чего загрузка получает статус `failed`. Загрузки без активности старше 24 часов и их `.part` удаляются автоматически; срок настраивается через окружение.

## Потоковое воспроизведение

`GET /api/tracks/{id}/stream` проверяет сессию и поддерживает один HTTP byte range. Для MVP Node читает файл самостоятельно. В production следует передавать выдачу nginx через `X-Accel-Redirect`, сохраняя проверку прав в API.

При `X-Accel-Redirect` пользователь nginx получает ACL только `rX` на каталоги
`storage/originals`, `storage/derived` и `storage/covers`, а также traverse (`--x`)
на их родителей. ACL по умолчанию наследуется новыми media-файлами. Добавлять
nginx в группу приложения нельзя: иначе он сможет прочитать `.env` и закрытый
ключ `storage/federation/identity.json`.

## Каталог

- `GET /api/tracks?q=&artist=&album=&sort=` — поиск, точные фильтры и серверная сортировка.
- `GET /api/catalog` — агрегированные исполнители и альбомы с количеством треков.
- `PATCH /api/tracks/{id}` — редактирование пользовательских метаданных.
- `DELETE /api/tracks/{id}` — удаление записи, оригинала и извлечённой обложки.
- `PUT/DELETE /api/tracks/{id}/cover` — установка пользовательской обложки (до 12 МиБ, сервер конвертирует её в JPEG) и удаление обложки.

Допустимые сортировки: `newest`, `oldest`, `title`, `artist`, `album`, `year`.

## Персональная медиатека

- `PUT /api/tracks/{id}/like` — добавить сердечко;
- `DELETE /api/tracks/{id}/like` — убрать сердечко;
- `GET /api/tracks?liked=1` — системная коллекция «Мне нравится»;
- `GET/POST /api/playlists` — личные плейлисты;
- `PATCH/DELETE /api/playlists/{id}` — название и удаление плейлиста;
- `POST/DELETE /api/playlists/{id}/tracks[/{trackId}]` — состав плейлиста;
- `POST /api/history` — отметить начало прослушивания.
- `GET /api/history` — личная история до 200 треков;
- `GET/PUT /api/playback-state` — текущий трек, позиция, очередь, shuffle и repeat.

Web-клиент хранит показанный каталог отдельно от очереди воспроизведения. Смена вкладки или поиск не обрывают очередь. Очередь можно переставлять, сокращать и дополнять командой «Играть следующим»; её идентификаторы сохраняются через `playback-state`. Media Session API связывает плеер с системными элементами управления браузера и Android.

Сердечко не меняет общий каталог и не создаёт копию файла. «Мне нравится» является системной выборкой из `track_likes`, а не удаляемым плейлистом. `owner_id` трека означает загрузившего и используется для прав удаления, но не ограничивает видимость каталога.

## Известные ограничения

- Вся библиотека общая для авторизованных пользователей.
- Нет отдельного CSRF-токена; вместо него действует строгая проверка `Origin` и `SameSite=Strict`.
- Нет ротации/просмотра сессий.
- Нет waveform и ReplayGain; AAC 192/96 создаются по требованию и учитываются в `track_files`.
- Индексация пока выполняется внутри процесса API, а не отдельным worker.
- Worker пока работает внутри процесса API и обрабатывает задания последовательно.

## Рекомендуемое production-размещение

```text
клиент -> reverse-proxy:443 (TLS, обязательная авторизация приложения)
       -> app-host:80 (внутренний nginx)
       -> 127.0.0.1:8095 (Node API/web)
       -> 127.0.0.1:5432 (PostgreSQL)
```

Конкретные домены, IP-адреса, пути, имена узлов и расположение резервных копий
должны храниться вне репозитория. Секреты задаются через локальный `.env` с
минимально необходимыми правами доступа.

API и фоновые задачи запускаются отдельными systemd-сервисами. API принимает
HTTP-запросы, проверяет авторизацию и ставит задания в PostgreSQL. Worker с
параметром `--worker` обрабатывает загрузки, распознавание, транскодирование и
ротацию диагностических отчётов. В production авторизованный API передаёт
проверенный путь nginx через `X-Accel-Redirect`; Range и `sendfile` выполняются
nginx без загрузки Node.js передачей аудиобайтов.

### Импорт удалённых оригиналов

Лайк удалённого трека атомарно создаёт временную персональную запись и задание
`federation_remote_replicas`. Worker скачивает оригинал подписанным Range-запросом
в `.part`, продолжает его после рестарта и сверяет полный размер и SHA-256.
После проверки создаётся обычный локальный `tracks`, оригинал переносится в
`storage/originals`, извлекается встроенная обложка и ставится локальный лайк.
Временный федеративный лайк удаляется. Если такой SHA-256 уже хранится дома,
второй файл и трек не создаются: пользовательский лайк привязывается к найденному
локальному треку. `track_sources` оставляет только техническое происхождение для
защиты от повторного импорта; доступность, доверие и дальнейшее удаление объекта
на origin никак не влияют на готовый локальный трек.

## Целевая модель

Следующие сущности: `artists`, `albums`, `track_files`, `user_library`, `favorites`, `playlists`, `playlist_tracks`, `play_history`, `invitations`, `devices`, `processing_jobs`.

Будущий pipeline:

```text
uploading -> verifying -> queued -> processing -> ready
                         |              |
                         +-----------> failed
```

Оригинал хранится один раз. Производные Opus/AAC и обложки связываются через `track_files`.

## Совместимость API

Стабильные маршруты опубликованы под `/api/v1` и описаны в `API_V1.md`. Старые `/api/*` оставлены как временный compatibility layer и помечаются заголовком `Deprecation: true`. Нельзя удалять поля или менять смысл опубликованных v1-ответов без новой версии API.

## Будущая федерация

Закрытая федерация планируется отдельным межсерверным протоколом `/federation/v1`; Android и WEB продолжат обращаться только к домашнему `/api/v1`. Домашний сервер объединит каталоги и будет проксировать удалённые Range-потоки, поэтому недоступность peer не должна мешать локальной библиотеке. Полный план и модель доверия зафиксированы в `FEDERATION.md`.
