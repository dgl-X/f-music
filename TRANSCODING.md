# План транскодирования

> На гипервизоре установлена GTX 1660 SUPER, однако её NVENC предназначен для видео. AAC 192/96 и возможный Opus остаются CPU-задачами; проброс этой GPU в VM не ускорит текущий музыкальный pipeline.

Оригинал всегда остаётся неизменным и является главным источником. Android выбирает оригинал либо готовую AAC-производную по сетевому профилю; если производная ещё строится, воспроизведение сразу начинается с оригинала.

## Реализованные варианты

- `original` — исходный файл без преобразования;
- `aac_192` — AAC-LC в M4A, около 192 кбит/с; основной универсальный вариант для мобильной сети;
- `aac_96` — AAC-LC в M4A, около 96 кбит/с; экономичный мобильный вариант.

Lossless-оригиналы FLAC не заменяются lossy-файлами. Производные создаются один раз фоновым worker и переиспользуются всеми пользователями.

## Целевая модель

Таблица `track_files`: `id`, `track_id`, `variant`, `mime_type`, `codec`, `bitrate`, `size_bytes`, `storage_key`, `status`, `created_at`. Уникальность — `(track_id,variant)`.

Файлы размещаются в `storage/derived/<variant>/<shard>/<track-id>.m4a`. Запись атомарно переименовывается после успешного `ffmpeg`; состояние хранится в `track_files`, а встроенный worker обрабатывает очередь по одному файлу.

## API

Текущий стабильный маршрут расширяется без поломки v1:

```text
GET /api/v1/tracks/{id}/stream?quality=auto|original|high|compact
```

`high` означает `aac_192`, `compact` — `aac_96`. Явный профиль ждёт создание производной до 60 секунд и не загрязняет его cache-key оригиналом. `auto` выбирает готовый `aac_192`, а при отсутствии временно отдаёт оригинал и ставит обработку в очередь. Ответ сообщает фактический вариант заголовком `X-Music-Variant`. Range сохраняется для всех вариантов.

## Порядок реализации

Production-проверка 1 сентября 2026 успешно создала варианты AAC 192 и AAC 96, включая HTTP Range. Массовая предварительная генерация всей библиотеки пока не запускается: производные создаются по фактическому спросу.

Повторяемое измерение профилей выполняется без изменения медиатеки:

```bash
scripts/benchmark-transcoding.sh /путь/к/аудиофайлу 3
```

Скрипт использует те же параметры FFmpeg, что и worker, выполняет по три прогона
AAC 96 и AAC 192 и показывает время, пиковую RSS, размер результата и отношение
длительности записи ко времени кодирования. Временные производные удаляются после
завершения.

## Измерение на типовой VM

Контрольный прогон 8 сентября 2026 года выполнен внутри production-VM с 8 vCPU
на исходнике длительностью 189,87 секунды. Результат — среднее двух прогонов:

| Профиль | Скорость | Время обработки | Размер | Пиковая RSS процесса |
| --- | ---: | ---: | ---: | ---: |
| AAC 96 | 33,21x | 5,72 с | 2 364 367 байт | около 57 МиБ |
| AAC 192 | 26,95x | 7,05 с | 4 808 601 байт | около 57 МиБ |

Параллелизм в два задания оставляет большой запас для домашнего сервера: даже
более тяжёлый профиль обрабатывает трек примерно в 27 раз быстрее воспроизведения,
а два процесса FFmpeg требуют около 114 МиБ дополнительной RSS. GPU для этих
профилей не используется.
