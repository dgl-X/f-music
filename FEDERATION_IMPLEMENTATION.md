# План внедрения федерации Family Music

Статус: черновик 0.2. Этот документ превращает [`FEDERATION.md`](FEDERATION.md) в небольшие независимо выпускаемые части.

Текущее состояние на 8 сентября 2026 года:

- чистая тестовая нода развёрнута отдельно от production;
- добавлены JSON Schema описания узла, приглашения, ошибки и delta;
- добавлен воспроизводимый Ed25519/Content-Digest тестовый вектор;
- CI-тесты используют замороженные descriptor/delta fixtures предыдущего профиля
  v1 и проверяют rolling upgrade в обе стороны;
- согласование major/minor и capabilities выполняется единым модулем: отсутствие
  необязательных новых функций даёт `limited`, а отсутствие обязательной —
  `upgrade_required`;
- delta с поддерживаемым `min_reader_minor` и неизвестными необязательными полями
  принимается, а требующая более новый reader отклоняется до изменения cursor;
- на тестовой ноде доступен административный WEB-мастер создания identity и настройки endpoints;
- до явного включения `/federation/v1/node`, `/federation/v1/health` и `/.well-known/family-music` отвечают `404`;
- реализованы совместимые с тестовым вектором подпись RFC 9421, Content-Digest, окно времени и защита nonce от replay;
- WEB умеет проверять endpoint с TLS, DNS pinning и запретом SSRF/DNS rebinding; private endpoint требует точный RFC1918 IP;
- WEB создаёт и отзывает 15-минутные одноразовые приглашения; pairing-секрет хранится только как SHA-256 и показывается один раз;
- реализован подписанный `POST /federation/v1/pairing/accept`, двустороннее подтверждение challenge, одноразовое погашение приглашения и защита от pairing с собой;
- WEB принимает код приглашения, показывает закреплённые identity/endpoint/совместимость peer и позволяет отозвать локальное доверие;
- pairing испытан между production и отдельной тестовой нодой через разные публичные HTTPS-endpoint: обе стороны закрепили разные identity со статусом `compatible`, приглашение погашено один раз;
- часть 2 завершена на базовом профиле протокола 1.0;
- реализован этап 3A: политика `none/all`, начальный снимок, автоматический журнал `track.upsert.v1`/`track.delete.v1` и подписанная delta до 500 событий;
- production успешно отдал тестовой ноде первую страницу из снимка 567 треков; повтор того же подписанного запроса отклонён как replay;
- реализован этап 3B: отдельный удалённый индекс, проверка подписи точного тела ответа, cursor, постраничный worker и экспоненциальный backoff с jitter;
- двусторонняя проверка импортировала 100 треков test в production и 567 треков production в test без аудиофайлов; обе стороны завершили синхронизацию без ошибок.
- живой цикл update/delete подтверждён: изменение тестового трека пришло как revision 101, удаление как `track.delete.v1` revision 102, после чего объект исчез из production-индекса; исходный файл и обложка остались только ответственностью origin-ноды.
- добавлен `catalog.notify.v1`: origin отправляет подписанную только подсказку о новой head revision, получатель немедленно будит обычную delta-синхронизацию; payload изменений через notify не передаётся;
- контрольный polling сохранён раз в 5 минут, локальная проверка входящего сигнала выполняется раз в 5 секунд, ошибки notify имеют независимый экспоненциальный backoff с jitter;
- живой тест revisions 103/104 доставил изменение и его откат с test в production через notify без ошибок; пропуск notify по-прежнему восстанавливается очередным polling.

## Основной принцип обновлений

Обновление Family Music не должно требовать синхронного обновления всех узлов. Локальный `/api/v1`, локальные файлы и пользовательские данные работают независимо от состояния федерации.

Каждый узел сообщает отдельно:

- `software_version` — только для диагностики;
- поддерживаемые major-протоколы, например `[1]`;
- `federation_minor` — реализованный уровень внутри major;
- `capabilities` — реально доступные функции;
- `required_capabilities` — обязательный минимум конкретного ответа/операции.

Функция включается только при наличии capability с обеих сторон. Сравнивать версии приложения и угадывать возможности по номеру запрещено.

## Политика версий протокола

Путь содержит major: `/federation/v1`. Несовместимое изменение создаёт `/federation/v2`; смысл существующих полей v1 не меняется.

Внутри v1 разрешены только совместимые изменения:

- добавление необязательного поля;
- добавление необязательной capability;
- новый endpoint, не требуемый старыми сценариями;
- новый тип события, явно помеченный как необязательный.

Запрещены без нового major:

- удаление или переименование поля;
- смена типа или смысла поля;
- изменение алгоритма подписи/канонизации;
- превращение необязательного поля в обязательное;
- изменение семантики cursor, revision или tombstone.

JSON-reader обязан игнорировать неизвестные поля. Отсутствующее необязательное поле получает документированное безопасное значение. Порядок полей JSON не значим.

## Согласование возможностей

`/.well-known/family-music` и `GET /federation/v1/node` возвращают, например:

```json
{
  "software_version": "1.4.0",
  "protocols": {"1": {"minor": 3}},
  "capabilities": {
    "pairing.v1": {},
    "catalog.delta.v1": {"max_page": 500},
    "stream.range.v1": {"variants": ["original", "aac_96", "aac_192"]},
    "covers.v1": {}
  }
}
```

Capability имеет стабильное имя с собственной версией. Новая реализация может поддерживать одновременно `catalog.delta.v1` и будущую `catalog.delta.v2`.

Состояния узла в WEB:

- `compatible` — общий major и все используемые capability доступны;
- `limited` — связь работает, но часть новых возможностей отсутствует;
- `upgrade_required` — нет общего major или не хватает обязательной capability;
- `offline` — совместимость неизвестна из-за недоступности;
- `revoked` — доверие отозвано.

`limited` — нормальное состояние rolling upgrade, а не ошибка.

## Совместимость событий синхронизации

Каждая delta-страница содержит:

```json
{
  "protocol_version": 1,
  "producer_minor": 3,
  "min_reader_minor": 1,
  "items": [],
  "next_cursor": "opaque"
}
```

У события есть `type`, `event_version` и `critical`.

- Неизвестное `critical=false` можно пропустить, записать в аудит и продвинуть cursor.
- Неизвестное `critical=true` останавливает эту синхронизацию без продвижения cursor и переводит peer в `upgrade_required`.
- `track.upsert.v1` и `track.delete.v1` являются обязательной базой major v1.
- Старый peer никогда не должен удалить локальный индекс только потому, что не понял новое необязательное поле.

Origin обязан выдавать старому peer только тот формат, который был согласован в `/node`. Новое представление не отправляется лишь потому, что origin уже обновился.

## Cursor и обновления

Cursor непрозрачен, но сервер хранит рядом negotiated major/capability set. После обновления:

- совместимый набор продолжает старый cursor;
- смена формата требует подписанного `cursor_reset_required`;
- до успешной пересборки прежний удалённый индекс остаётся доступен как устаревший;
- tombstone применяется только после полной проверки подписи и поддерживаемой версии.

Миграции локальной PostgreSQL не видны peer и выполняются назад-совместимо: сначала добавить nullable/default поля, затем выпустить код, и только в более позднем релизе удалять внутренний legacy-код.

## Срок поддержки

Пока существует только v1, все релизы федерации обязаны взаимодействовать с базовым профилем v1 (`pairing.v1`, `catalog.delta.v1`, tombstone и подписи v1).

При появлении v2:

- узел некоторое время обслуживает v1 и v2 параллельно;
- отключение v1 возможно не раньше двух стабильных релизов и 90 дней после появления v2;
- WEB заранее показывает peer, которые потеряют связь;
- администратор может временно запретить auto-upgrade протокола для конкретного peer.

## Части внедрения

### Граница автоматизации

Первичную установку пакетов, PostgreSQL, nginx и systemd выполняет установщик на самой машине. После первого запуска дальнейшее управление федерацией выполняется из WEB без редактирования `.env`, SQL и файлов ключей вручную.

В административных настройках появится раздел «Федерация», который позволяет:

- включить или выключить федерацию;
- автоматически создать identity и показать безопасный fingerprint;
- указать публичные и внутренние endpoints с проверкой доступности;
- экспортировать зашифрованную резервную копию identity и восстановить её;
- создать одноразовое приглашение как QR-код или строку;
- принять приглашение, увидеть согласованные возможности и состояние узла;
- отозвать доверие, перепроверить endpoint и посмотреть журнал соединений.

Закрытый ключ никогда не показывается WEB в открытом виде. Обычный пользователь не видит этот раздел. Выключение федерации не удаляет identity и настройки без отдельного подтверждения администратора.

### Часть 0 — контракт и тестовый стенд

- Зафиксировать JSON Schema для `/node`, приглашения, ошибки и delta.
- Сделать тестовые векторы Ed25519/RFC 9421 и Content-Digest.
- Добавить contract-тесты: новая нода как клиент старой и старая как клиент новой.
- Подготовить отдельную БД/каталог/пользователя для тестового узла.
- Federation feature flag по умолчанию выключен.

Результат: production не меняет поведение; два тестовых процесса проходят матрицу совместимости.

Текущий прогресс: базовая матрица закреплена fixtures профиля v1.0. Текущая нода
договаривается со старой как `limited`, если общий обязательный минимум доступен,
и не угадывает возможности по `software_version`. Проверка delta учитывает
`producer_minor` и `min_reader_minor`; неизвестное обязательное событие и слишком
новый обязательный minor не продвигают cursor.

### Часть 1 — identity и transport

- Генерация/резервная копия Ed25519 identity.
- Административный WEB-мастер включения, создания identity и настройки endpoints.
- `node_id`, `/.well-known/family-music`, `/federation/v1/node` и `/health`.
- Проверка endpoint для домена, белого IP и точного private IP.
- TLS CA либо SPKI pin, подписи, nonce, clock skew, rate limit и аудит.

Результат: узлы безопасно проверяют друг друга, но ничего не экспортируют.

### Часть 2 — ручное pairing

- Одноразовое приглашение, QR/строка, accept и двустороннее подтверждение.
- WEB-страница peer: fingerprint, endpoint, состояние и revoke.
- Negotiation major/minor/capabilities и состояния `compatible/limited/...`.

Результат: основной сервер и тестовая нода сопряжены через WEB, каталог ещё закрыт.

### Часть 3 — экспорт метаданных

- Policy `none/all/albums/collections`.
- Revision log, `track.upsert.v1`, `track.delete.v1`, cursor и reset.
- Таблицы удалённого индекса и worker sync с backoff/jitter.
- Ограничение ответа 500 элементов и tombstone при отзыве объекта.

Результат: WEB администратора видит импортированный индекс, пользовательский поиск пока не меняется.

Текущий прогресс: 3A и 3B работают на двух нодах. Удалённые данные хранятся отдельно от локальных треков, события применяются по возрастанию revision, update/delete проверены на реальном треке, а состояние peer и ошибки синхронизации видны администратору. Реализованы глобальные политики `none/all/albums/collections`: администратор собирает именованные коллекции из локальных треков и выбирает опубликованные альбомы либо коллекции в WEB. Для каждого доверенного peer можно наследовать общую политику или независимо назначить `none/all/albums/collections`. Изменение состава и правил создаёт совместимые события `track.upsert.v1`/`track.delete.v1`; каталог, обложка и оригинальный поток проверяют одну и ту же эффективную политику.

API создания коллекции, замены её состава и назначения индивидуального правила
проверяется на установленной ноде командой
`node scripts/federation-export-policy-smoke.mjs /opt/family-music/.env`. Сценарий
создаёт временного администратора и коллекцию, использует два реальных локальных
трека, затем восстанавливает настройки и удаляет тестовые данные.
Параметр `--hold-seconds=N` оставляет правило активным на ограниченное время для
двусторонней проверки. Закрытый объект проверяется подписанным запросом через
`scripts/federation-acl-deny-smoke.mjs`.

10 сентября 2026 живой тест между test и production подтвердил переход удалённого
индекса `102 → 1 → 102`, `206` для разрешённого Range, `403 track_not_shared` для
трека вне коллекции, потоковый лимит `200,200,200,200,429` и полную автоматическую
очистку временного пользователя, коллекции и правила.

### Часть 4 — чтение каталога

- Объединённый поиск и явный badge origin.
- Удалённые страницы трека, артиста и альбома.
- Недоступный peer отображается без блокировки локальных результатов.

Результат: метаданные доступны пользователям, аудио ещё выключено.

Текущий прогресс: реализован объединённый поиск локальных и удалённых метаданных с явным источником, online/offline-состоянием и безопасной opaque remote reference. Удалённая карточка показывает связанные треки/альбом, позволяет начать воспроизведение и сохранить локальный лайк; редактирование метаданных origin по-прежнему запрещено. Поиск испытан на production по реальному индексу test-ноды.

### Часть 5 — поток

- Подписанный Range endpoint origin.
- Домашний proxy, ETag/416, лимит одновременных потоков.
- Сначала AAC 96/192; оригинал только отдельным permission.
- LRU по peer, общий лимит, таймауты и circuit breaker.

Результат: удалённый трек воспроизводится через домашний сервер.

Текущий прогресс: реализован подписанный origin endpoint и домашний streaming proxy с Range (`206/416`) и ограничениями 4 входящих/6 исходящих потоков на peer. По явному решению владельца доверенным сопряжённым нодам передаётся оригинальный MP3/FLAC через домашний proxy, поэтому первый запуск не ждёт транскодирования. AAC 96/192 остаются совместимыми вариантами протокола. Удалённое прослушивание не записывается в локальную историю, но трек можно сохранить в состоянии очереди.

### Часть 6 — пользовательские ссылки

- Remote reference в локальной очереди, лайках и плейлистах.
- Восстановление после перезапуска и понятное offline/revoked состояние.
- Android продолжает использовать только домашний `/api/v1`.

Текущий прогресс: часть 6 завершена. WEB сохраняет персональные лайки, смешанную очередь и плейлисты с opaque remote reference. Сохранённые ссылки не исчезают при проблемах связи или отзыве доверия: они получают `offline` либо `revoked`, остаются видимыми и не запускаются до восстановления доступа. Поиск при этом показывает только активные ноды. Старые Android-клиенты продолжают видеть и изменять локальную часть без ошибок. На тестовой ноде проверены лайк, очередь, плейлист и искусственное offline-состояние с последующим восстановлением peer.

### Часть 7 — эксплуатация и hardening

- Метрики peer/sync/stream/cache для администратора и позднее Zabbix.
- Ротация аудита и очистка отозванного кэша.
- Тесты replay, SSRF, DNS rebinding, key/endpoint replacement, partial Range и DoS.
- Документация установки/обновления/отката.

Текущий прогресс — часть 7 завершена. Административный `/api/v1/admin/metrics` показывает активные, offline и отозванные ноды, размер удалённого индекса, ссылки в лайках/плейлистах, ошибки sync/notify, возраст синхронизации и текущие входящие/исходящие потоки. WEB выводит сводку в общей статистике. Для Zabbix добавлен отдельный `/api/v1/metrics/zabbix` с отзывным Bearer-токеном и урезанным ответом без личных данных и адресов узлов; готов UserParameter с одним JSON master-item. Worker каждые шесть часов удаляет истёкшие nonce и приглашения старше 30 дней, не затрагивая каталог и пользовательские ссылки. Лимиты потоков учитывают только реально занятые слоты и гарантированно освобождают их при обрыве клиента. Двусторонний живой тест подтвердил лимит 4 входящих потоков (`200,200,200,200,429`), освобождение после обрыва, partial Range `206`, ошибочный Range `416` и восстановление следующего запроса. DNS/SSRF-фильтр дополнительно закрывает полные и IPv4-mapped представления приватных IPv6-адресов.

## Матрица обязательных тестов релиза

Для каждого изменения федерации CI поднимает минимум три узла:

| Клиент | Сервер | Ожидание |
|---|---|---|
| текущий | текущий | все новые capability |
| текущий | предыдущий | базовые функции, состояние `limited` |
| предыдущий | текущий | старый формат ответа, без ошибок парсинга |
| текущий | без общего major | `upgrade_required`, локальная музыка работает |
| текущий | offline | backoff/circuit breaker, локальная музыка работает |

Также обязательны rolling upgrade A→новый при старом B, затем B→новый, и обратный порядок.

## Ближайшая практическая задача

Импорт из чужой библиотеки, включая внешние обложки и переход карточки к созданному локальному треку, завершён. В GitHub Actions добавлен отдельный прогон на двух независимых PostgreSQL-базах. Он проверяет применение `track.upsert.v1`/`track.delete.v1`, изоляцию локальной библиотеки, игнорирование необязательного события будущей версии и полный откат страницы при неизвестном обязательном событии.

Следующий шаг совместимости — при появлении первого серверного release-тега закрепить его как `compatibility baseline` и выполнять ту же матрицу сначала старым reader с новым producer, затем новым reader со старым producer. До появления тега роль базового профиля выполняют схемы и векторы протокола v1.

7 сентября 2026 выполнен живой rolling-тест: тестовая нода обновлена до пакета `0.1.0-6`, основная оставлена на предыдущем серверном коде. Обе стороны завершили синхронизацию со статусом `compatible`, без ошибок и повторов; API, PostgreSQL, storage и оба worker остались исправны. Таким образом проверены оба направления обмена — новый reader со старым producer и старый reader с новым producer.

В тот же день `scripts/federation-reconnect-smoke.mjs` выполнен в обоих направлениях на живых нодах. Тест временно подменяет endpoint конкретного peer, ожидает управляемую ошибку stream и состояние `retry`, восстанавливает endpoint, проверяет partial Range и завершение локального импорта, а затем удаляет тестового пользователя, лайк, реплику и созданный файл. В секции `finally` endpoint возвращается даже при ошибке теста.
